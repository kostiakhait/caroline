# Pinned dependency set for running backend-py under the Linux shell's
# bundled runtime/python (see linux-shell/provision_runtime.sh). Captured via
# `pip freeze` after iteratively resolving every ModuleNotFoundError hit by
# `from app.main import PORT, app` on a clean python-build-standalone
# CPython 3.12.15 interpreter -- NOT the full backend-py dependency set for
# every platform. pywin32/edge-playback (genuinely Windows-only
# automation extras) are intentionally absent; those plugins fail to import
# on Linux and are skipped, same as already verified in earlier Linux-port
# phases.
#
# Corrected 2026-10-21 (Linux parity pass, messenger-integrations testing
# plan): this file's own header used to ALSO claim playwright was a
# Windows-only extra -- wrong, contradicted by live code.
# app/plugins/app_browser_cdp.py and _linux_app_browser.py (Phase 3 of
# docs/LINUX_PORT_PLAN.md, done and verified 2026-10-05) both import
# playwright directly and ARE the Linux embedded-browser path; it was
# simply never added to this pin file, so every Linux provision has been
# silently missing it (loader.py's own per-plugin import-failure catch
# masked this rather than crashing the backend, so it went unnoticed).
# Added here, pinned to the same version the Windows runtime ships.
# Also added: qrcode, Pillow -- needed by whatsapp_channel.py's and
# signal_channel.py's QR-login image generation, same gap, same cause
# (never added when those channels landed).
#
# Added 2026-10-24 (continuous-narration testing): edge-tts (+ tabulate, which it needs). It was listed as
# Windows-only above, but it is plain Python on aiohttp; without it every voice synthesis on Linux fell
# back to Camerlengo's ai:tts (9.3s for a 64-character sentence, measured), and a voice remark every few
# seconds could not keep up. local_edge_tts.py is the only importer.
#
# Added 2026-10-22 (sw-mode testing, documents category): python-docx,
# openpyxl, python-pptx, reportlab, lxml, XlsxWriter, et_xmlfile -- the
# document libraries the Windows runtime ships (same versions) and the
# models are told to use through run_python (shell_plugin.py names
# python-pptx/python-docx). None of them were here, so on Linux every
# "make a Word/Excel/PowerPoint/PDF file" task had nothing to work with.
#
# Regenerated 2026-10-16, same incident: re-ran the iterative resolution for
# the first time since the Slack/Telegram/Discord messenger integrations
# landed (2026-10-06 onward) -- aiohttp, slack_sdk, telethon and discord.py
# (plus their own transitive deps) had never been added here, so a fresh
# Linux provision failed on `from app.main import PORT, app` the moment it
# reached app/slack_channel.py's own import. Regenerating this file isn't a
# one-off fix: provision_runtime.sh's own verify step is the thing that
# would have caught this immediately -- it just hadn't been run live since.
#
# Also gained python-xlib (2026-10-16, same pass): linux-shell/caroline_
# shell.py (the Linux launcher, a separate entry point from app.main, but
# installed into this SAME shared runtime/python by provision_runtime.sh)
# imports it via hotkeys.py for its global-hotkey X11 grab -- there is no
# separate requirements file for linux-shell/, so this file now covers
# both entry points that share this one runtime, not just backend-py's own
# `from app.main import PORT, app` check. Found the same way: a real
# AppImage built from provision_runtime.sh's own output failed at startup
# with ModuleNotFoundError: No module named 'Xlib', confirmed live on a
# fresh xopek-desktop test container (2026-10-16) -- this verify step had
# apparently never been run end-to-end since the hotkey feature was added.
