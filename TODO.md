# Caroline — TODO

Портативный standalone-чатбот: те же возможности, что у Claude Code в этом
репозитории (почта, notes, браузер/Windows-автоматизация), но без VS Code —
трей-приложение с горячей клавишей. См. `README.md` за архитектурой и
внешними требованиями.

## Сделано

- [x] Backend-сайдкар (`backend/`): WebSocket-сервер + Claude Agent SDK
      streaming `query()`, watchdog с автоперезапуском зависшей/упавшей
      сессии (замена сообщения проигрывается заново автоматически).
- [x] Портативность: своя рабочая директория
      (`%LOCALAPPDATA%\Caroline\workspace\`), дефолтные MCP-серверы
      скопированы в `backend/mcp-servers/` (без ссылок на `D:/REPO/silmarillion`
      в рантайме), зарегистрированы под именами `caroline-*` в user scope при
      первом запуске (`claude mcp add --scope user`) — без коллизий с чужим
      конфигом и без interactive-approval гейта, который блокирует
      project-scoped `.mcp.json` в headless-сессии.
- [x] `control.ts`: `claude auth login/status/logout`, `claude mcp
      add/remove/list` через тот же bundled `claude.exe` — протокол
      `control_request`/`control_response` поверх WebSocket. Авторизация
      подтверждена вживую: подхватывает уже залогиненную на машине Claude
      CLI-сессию/подписку автоматически (учётка привязана к Windows-юзеру,
      не к конкретной установке) — ожидаемое поведение, не баг.
- [x] WPF-оболочка: трей-иконка, глобальный хоткей (по умолчанию Ctrl+Alt+C),
      WebView2 с локальным chat.html/css/js (стиль squirrel_wisdom/Ratatosk),
      сворачивание в трей по крестику vs обычный minimize в таскбар,
      `BackendProcess` спавнит/убивает `node backend/dist/server.js`.
- [x] `build.bat`: сборка backend + бандлинг MCP-серверов + self-contained
      publish WPF в `dist/`. Плюс `Caroline.csproj`: MSBuild-таргет
      `SyncBackendDist` копирует свежий `backend/dist/*.js` в вывод сборки
      при каждом `dotnet build` — раньше эта копия обновлялась только
      вручную, из-за чего однажды запущенное приложение молча исполняло
      старый backend без ошибок (баг с пустыми полями Personality).
- [x] Арт: иконка приложения (.ico) + трей-иконка (цветная иллюстрация,
      сгенерирована через beautysqrl.com `generateImage` + chroma-key,
      `Caroline/art/gen_art.py`) и прозрачный сплэш (`SplashWindow.xaml`,
      `AllowsTransparency`, висит фиксированные 3 сек перед показом
      основного окна, клик закрывает раньше). Проверено вживую.
- [x] Markdown → rich text, статус-бар для tool-use вместо основного
      диалога, Settings-панель (логин, MCP add/remove/list, теперь и
      Personality/Voice) — всё проверено вживую.
- [x] Загрузка/чтение файлов из чата: картинки и PDF — inline
      content-блоки (`image`/`document`, base64) прямо в `SDKUserMessage`;
      txt/код/офисные документы — сохраняются в `workspace/uploads/` и в
      сообщение добавляется путь для штатного Read-тула. **Известное
      ограничение**: офисные форматы (docx/xlsx/pptx) не гарантированно
      парсятся Read-тулом — не проверено вживую, возможно потребуется
      отдельный конвертер.
- [x] Личность (`persona.ts`): поля Name/Gender/Age/Bio в Settings,
      дефолт — независимая женщина-секретарь средних лет, применяется
      через `systemPrompt: {type:'preset', preset:'claude_code', append}`.
      Проверено вживую (после починки бага со старой копией backend).
      Меняется только на следующий рестарт сессии, не мгновенно.
- [x] Персистентность диалога: транскрипт в localStorage WebView2-профиля
      (переживает перезапуск приложения) + `continue: true` на бэкенде,
      чтобы и сама модель помнила контекст между запусками, не только UI.
      **Не проверено вживую** (не тестировали закрыть → открыть → диалог
      на месте).
- [x] Голосовой ввод/вывод: кнопка микрофона (`MediaRecorder`, паттерн
      как в `squirrel_wisdom/portal/chat.js`), STT/TTS через
      `beautysqrl.com` (`.command: "stt"/"tts"`), автоотправка голосовых
      сообщений по умолчанию (настраивается в Settings), автоозвучка
      ответа на голосовой запрос, кнопка 🔊 на текстовых. **Не проверено
      вживую** — код готов и компилируется, но реальную запись/STT/TTS
      через WebView2 не гоняли живьём.

- [x] **Инсталлятор** (`Windows/CarolineInstaller/`, порт `d:\REPO\AppleKey`'s
      `AppleKeyInstaller`): тонкий WPF-бутстрапер, без прав администратора,
      всё per-user под `%LocalAppData%\Caroline\`. Скачивает `Caroline.zip`
      с `downloader.multi-portal.org/apps/caroline/` (SHA-256 проверка),
      идемпотентно ставит **изолированный** Node.js (`runtime\node\`,
      портативный zip с nodejs.org, никогда не трогает PATH/системный
      Node) и **изолированный** Python (`runtime\python\`, embeddable zip
      с python.org, тоже без PATH/реестра), затем ставит Chromium для
      Playwright (через `playwright-core`'s `cli.js`, только если
      `chromium.executablePath()` ещё не резолвится в реальный файл —
      кэш стандартный `%LOCALAPPDATA%\ms-playwright`, не изолирован
      специально, это repo для браузерных бинарников самого Playwright).
      24 баннера встроены в exe (`Assets\Banners\*.png`) и крутятся в UI
      каждые 6 сек. `BackendProcess.cs` обновлён: ищет
      `..\runtime\node\node.exe` относительно себя, иначе падает на
      `node` из PATH (для дев-сборок без инсталлятора). Собрано и
      скомпилировано (`build_installer.bat` прогоняет всю цепочку
      локально), **но ничего не залито на downloader.multi-portal.org** —
      это отдельный, ручной шаг (см. вывод `build_installer.bat`), и до
      него `DownloadsInfo.FetchAsync` будет получать 404.
- [x] `deploy.bat`: собирает (`build_installer.bat`) и заливает `Caroline.zip`
      + `.sha256` + `.version` + `CarolineInstaller.exe` на
      `downloader.multi-portal.org/apps/caroline/` через scp/ssh (тот же
      паттерн, что Ratatosk'овский `deploy.bat`). **Не запускался** — заливка
      на прод-сервер это отдельное ручное действие пользователя.
- [x] **Время / напоминания** (`scheduler.ts`): `schedule_reminder` /
      `list_reminders` / `cancel_reminder` — in-process SDK MCP-tool
      (`createSdkMcpServer`, без отдельного процесса), даёт самой модели
      возможность ставить себе "будильники". Хранится в
      `workspace/schedule.json` — переживает рестарт сессии и рестарт
      всего приложения; просроченные (пока приложение было закрыто)
      напоминания срабатывают сразу при следующем старте due-check
      loop'а. Срабатывание **проактивно** инжектится в текущую сессию
      (`ChatSession.injectProactive`) — модель продолжает диалог сама, не
      дожидаясь сообщения пользователя. **Проверено вживую end-to-end**
      (запланировал → сработало через 15 сек без участия пользователя →
      попало в chat.js как обычный ответ).
- [x] **Vault-политика для памяти/секретов** (`policies.ts`): если Notes
      залогинен, инструкция модели — секреты писать только в Notes,
      папка "Caroline:Vault" (не в локальные файлы), плюс раз в час
      (recurring-напоминание, `ensureRecurringBackup`) и один раз при
      закрытии приложения (`shutdown_sync` control-op, триггерится из
      `chat.js` на `pagehide` — единственная точка, где WebView2 реально
      выгружает страницу, а не просто сворачивается в трей) — бэкапить
      персону/напоминания в ту же папку. Закрытие best-effort: WPF ничего
      не ждёт перед `Process.Kill()`, так что подтверждения, что бэкап
      реально успел выполниться, нет. Также сказано, где лежит
      изолированный Python (`pythonPathInstruction`, путь совпадает с
      `AppPaths.PythonExe` инсталлятора) — не системный `python` на PATH.
      **Проверено частично**: рекуррентный бэкап-reminder сидируется и
      компилируется; сам факт, что модель реально пишет в Notes при
      срабатывании, живьём не гонялся.
