# Советник по инструментам (tool advisor)

## Context

У Caroline сейчас 203 инструмента в 45 плагинах (Telegram, WhatsApp, Signal, почта, заметки,
память, контакты и т.д.), и это число будет только расти -- по словам пользователя, в будущем
счёт пойдёт на тысячи. Каждый раз, выбирая, каким инструментом воспользоваться, модель либо
держит в голове весь этот каталог, либо тратит отдельный раунд на `get_tool_instructions`, чтобы
узнать детали конкретного инструмента перед вызовом. Цель -- сократить именно ЭТУ собственную
стоимость Кэролайн (не размер payload, уходящего в API: он не меняется).

Три решения, зафиксированные явно в разговоре (после нескольких неверных заходов, см. ниже
"Что это НЕ"):

1. **Это подсказка, не ограничение.** Полный доступ ко всем 203 (и будущим) инструментам у
   Кэролайн остаётся всегда. Советник никогда не убирает и не блокирует доступ к чему бы то ни
   было -- он только предлагает наиболее вероятный набор для конкретного сообщения.
2. **Зернистость -- отдельные инструменты**, не целые плагины (например, только
   `telegram_send_message` и `telegram_add_contact`, а не все 9 инструментов плагина telegram
   разом).
3. **Срабатывает на каждое реальное сообщение пользователя**, но НЕ через пересборку
   MCP-регистрации и НЕ через перезапуск/resume CLI-процесса -- это чисто текстовая подсказка,
   инжектируемая в промпт для этого одного хода, тем же механизмом, которым это уже делает
   `pending_interim_notes` внутри `submit()`.

Экономия конкретно в двух вещах (сформулировано пользователем):
- Кэролайн не нужно самой знать/перебирать сотни (а в будущем тысячи) инструментов.
- Для инструментов из подсказки советник сразу отдаёт полные подробности (не только имена) --
  это убирает отдельный вызов `get_tool_instructions` для них, то есть экономит целый
  раунд туда-обратно.

### Что это НЕ (отсеяно по ходу обсуждения, явно зафиксировано, чтобы не повторить ошибку)

- **НЕ** изменение набора реально зарегистрированных в MCP инструментов (`build_mcp_servers()`,
  `app/plugins/loader.py`). Та регистрация остаётся как есть, нетронутой.
- **НЕ** привязано к старту/перезапуску CLI-сессии (`_run_loop`, `app/chat_session.py:4453`) --
  этот процесс живёт много сообщений подряд через внутреннюю очередь (`submit()` ->
  `self.queue`), и никакой рестарт/resume под советника не нужен и не предполагается.
- **НЕ** жёсткий allow-list и не "эскейп-хэтч" вида `invoke_other_tool` -- такой механизм не
  нужен именно потому, что ничего и не ограничивается в первую очередь.
- **НЕ** хардкод конкретных инструментов/плагинов внутри самого советника -- он каждый раз
  читает живой каталог через `discover_plugins()`, так что новые плагины подхватываются сами,
  без правок кода советника.

## Design

### 1. Каталог инструментов -- `app/tool_advisor.py` (новый модуль)

- `_catalog() -> dict[str, ToolInfo]` -- строится один раз на процесс (ленивый memoized кэш:
  список плагинов статичен на время жизни процесса, хот-релоада нет), переиспользуется всеми
  вызовами. `ToolInfo`: `name`, `description`, `input_schema`, `plugin_name`.
- `_plugin_usage_instructions() -> dict[str, str]` -- `plugin_name -> usage_instructions`,
  тоже кэшируется один раз.
- Оба получены исключительно из `app/plugins/loader.py`'s `discover_plugins()` -- ни одного
  захардкоженного имени инструмента/плагина внутри `tool_advisor.py`.

### 2. Вызов советника

- `async def recommend_tools(user_text: str) -> str` -- возвращает собранный блок-подсказку,
  или `""` при любой неудаче/пустом результате (fail-open: никогда не поднимает исключение,
  никогда не задерживает ход дольше таймаута).
- Модельный вызов зеркалит уже существующий дёшевый классификатор в этой же кодовой базе --
  `small_model_engine.py`'s `_start_tier_index` (~строки 1229-1299): собрать
  `camerlengo_ai.AI(adapter=OpenRouterAdapter(api_key=get_model_provider_key()))` (переиспользуя
  уже существующий, защищённый от `None` импорт `camerlengo_ai` -- тот же паттерн, тот же
  вендоренный `AI.py`, тот же `app/model_key_provisioning.py`'s `get_model_provider_key()`),
  затем `await asyncio.wait_for(asyncio.to_thread(ai.resolve, PROMPT, model=cfg.AI_MODEL_SMALL,
  no_fallback=True), timeout=ADVISOR_TIMEOUT_S)` внутри `try/except Exception` -- ANY ошибка или
  таймаут превращается в `""`. `ADVISOR_TIMEOUT_S` ~2.5с (константа, подстраиваемая).
- Промпт советнику: компактный каталог (имя + однострочное описание на каждый инструмент, без
  JSON-схем -- сам вызов классификатора должен быть маленьким и быстрым) + текст сообщения
  пользователя (обрезанный, тем же способом, что уже используется в `_start_tier_index`'s
  `user_text[:2000]`) + инструкция вернуть JSON-массив самых вероятных имён инструментов (лимит
  `MAX_RECOMMENDED_TOOLS` ~12, константа, подстраиваемая).
- Разбор ответа защитный: любое имя, которого нет в реальном каталоге, молча отбрасывается
  (имени модели не доверяем бездумно); при ошибке разбора/пустом результате -- `""`.

### 3. Сборка блока-подсказки

Для каждого подтверждённого имени: `name(params) -- description`. Ниже -- дедуплицированный
`usage_instructions` каждого отдельного плагина, представленного в списке (только тех плагинов,
не всех 45). Обёрнуто явной формулировкой, что это подсказка, а не ограничение:

```
[Вероятно нужные для этого сообщения инструменты (это подсказка, не ограничение -- любой
другой инструмент доступен как обычно; весь список -- describe_own_backend):
- telegram_send_message(chat, text, account?) -- ...
- telegram_add_contact(phone, name?, account?) -- ...

Примечания по плагинам этих инструментов:
[telegram] ...полный usage_instructions...]
```

### 4. Точка вызова -- `app/chat_session.py`

- Пробросить флаг `is_real_user` через элемент очереди (`_push_message`, ~строки 2838-2855, и
  её вызывающего `submit()`), чтобы `_input_stream` мог отличить реальное сообщение пользователя
  от слэш-команд/внутренних нотификаций/watchdog-пингов -- подсказка собирается только для
  настоящих сообщений пользователя.
- Хук -- в `_input_stream` (`app/chat_session.py:2857-2865`), единственном асинхронном
  потребителе очереди, который и отдаёт сообщения прямо в SDK-поток
  (`await self.client.connect(self._input_stream())`, ~строка 4688): сразу после
  `item = self.queue.pop(0)`, до `yield item["message"]` -- если это реальное сообщение,
  `await recommend_tools(...)` на его тексте, и если результат не пуст, приклеить его тем же
  способом, каким `submit()` уже приклеивает `pending_interim_notes` (строки 2114-2121) --
  тот же паттерн, тот же стиль блока в квадратных скобках перед настоящим текстом.
- Объём первой итерации: только основной движок на Claude Agent SDK (`chat_session.py`).
  Отдельный путь `small_model_engine.py` (OpenAI/Camerlengo) пока не трогаем -- у него свой
  `build_tool_registry()`/своя сборка сообщений, и расширять туда разумно отдельным шагом после
  проверки механизма на основном движке, а не одним пакетом.

### 5. Явно не затронуто

- `build_mcp_servers()`/регистрация MCP (`app/plugins/loader.py`) -- без изменений. Все ~203
  инструмента остаются полностью зарегистрированными и вызываемыми как сегодня.
- Никакого перезапуска/resume процесса, ничего, привязанного к жизненному циклу CLI-процесса.
- Слэш-команды, внутренние нотификации (watchdog, реплей interim-notes, проактивные уведомления
  из мессенджеров) -- подсказка для них не собирается.

## Критические файлы

- `backend-py/app/tool_advisor.py` (новый) -- кэш каталога, `recommend_tools()`,
  промпт/разбор/форматирование.
- `backend-py/app/chat_session.py` -- пробросить `is_real_user` через `_push_message`/элементы
  очереди; вызвать `recommend_tools()` из `_input_stream` и приклеить результат, зеркаля
  приклеивание `pending_interim_notes` (строки 2114-2121).
- Переиспользуется без изменений: `app/plugins/loader.py`'s `discover_plugins()`;
  импорт-машинерия `camerlengo_ai` из `app/small_model_engine.py` (как образец для копирования,
  тот же вендоренный `AI.py`); `app/model_key_provisioning.py`'s `get_model_provider_key()`.

## Проверка

- Отдельный скрипт (в стиле `verify_telegram.py`/`verify_whatsapp.py`/`verify_signal.py` этой
  сессии): замоканный `ai.resolve`, возвращающий заскриптованный JSON-список имён (часть
  настоящих, часть выдуманных) против маленького фейкового каталога (3-4 фейковых
  Plugin/PluginTool) -- проверить: выдуманные имена отфильтрованы; для настоящих -- подробности
  (описание+схема+дедуплицированные usage_instructions плагинов) собраны верно; таймаут/ошибка/
  пустой ответ -- всегда `""`, без исключений.
- Отдельно -- форматирующая половина (`recommend_tools` без реального вызова модели) против
  РЕАЛЬНОГО каталога из `discover_plugins()` (все ~203 инструмента) с фиксированным списком имён,
  чтобы убедиться, что сборка не падает на настоящей форме каталога.
- Инжекция в `_input_stream`: лёгкий тест, который кладёт в очередь реальное сообщение
  пользователя и не-пользовательское, мокает `recommend_tools`, подтверждает, что блок
  приклеивается только к реальному сообщению, а при `recommend_tools() == ""` текст не меняется
  вообще.
- Живая проверка (по отдельному разрешению, как обычно, до любой сборки/деплоя): отправить
  несколько по-разному тематических сообщений, посмотреть реальный собранный блок в
  логе/транскрипте на релевантность и форматирование.
