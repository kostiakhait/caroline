## 1. Цель и рамки

Перевести память Caroline на микроагентную архитектуру. Микроагент — функция, внутри которой вызывается LLM через `AI.py`, как правило малой моделью, и которая решает одну узкую задачу.

Рамки этого этапа:

- Микроагенты прикручиваются **только к памяти**. Нарратор, перевод, определение языка и прочие существующие вызовы не переделываются.
- К памяти не относятся и в этот план не входят: кэш телефона (локальная копия SMS и контактов — источник данных, как почта) и события планировщика (`event_memory`).
- На микроагентов переносится не всё. Локальными инструментами (кэш SMS и контактов телефона, файлы и т. п.) главная модель пользуется сама и сама сводит ответы из разных источников.

Мотивация: память, оставленная на усмотрение главной модели, не используется. `working_memory.json` на рабочей машине не был создан ни разу; креденшиалы каждый раз ищутся в Notes заново. Надёжно работает только память, которую обслуживает код (`event_memory`, фоновые синки телефона).

## 2. Согласованная архитектура

### 2.1. Как память видит главная модель

Два инструмента: `save_info` и `request_info`. Вызывает их главная модель. Об устройстве памяти она ничего не знает.

### 2.2. Серверная часть (Camerlengo API)

Весь сервис памяти — часть API Камерленго.

```
save_info / request_info  (инструменты Caroline -> команды API)
        |
   диспетчер              микроагент: каких контролёров вообще звать
        |  (параллельно, каждый в своей нитке)
   контролёры памяти      по одному на вид памяти: «что здесь моё?» ->
        |                 вычленить и сохранить / найти и вернуть
   хранилища + индексы    контролёр никогда не видит хранилище целиком
```

Ответ на `request_info` — ответы контролёров с пометкой источника. Сводит их главная модель; микроагента-сборщика нет.

**Фон и мягкий таймаут** (решение 2026-10-10):
- `save_info` отдаёт текст фоновой задаче и отвечает сразу: факты у модели уже есть в диалоге. Стоп эту запись не прерывает. Модель узнаёт о записи, только если она не удалась, служебным сообщением.
- `request_info` читает через `memory:requestStart` / `memory:requestPoll`. Сервер отдаёт ответ порциями по мере нахождения: память фактов — каждой веткой дерева по отдельности (лист сам фильтрует и переводит найденное), остальные контролёры — целиком, когда готовы.
- Всё, что пришло за 30 секунд, становится ответом инструмента (`"status": "partial"`). Чтение продолжается в фоне, и каждая следующая порция сразу приходит модели служебным сообщением «[Additional facts from memory …]». Стоп прерывает это продолжение, как любой вызов инструмента.
- Фильтр и обратный перевод теперь идут порциями, а не одним вызовом: чтение дороже примерно в полтора-два раза.

### 2.3. Виды памяти и где они лежат

| Вид | Устройство | Где |
|---|---|---|
| Долговременная память фактов | дерево (раздел 2.4) | сервер, база памяти |
| Тематическая память, долгосрочная история | треки тем, журнал эпизодов | сервер, база памяти |
| Память документов | документы с кусками, дерево карточек (раздел 2.9) | сервер, база памяти |
| Тематическая память, краткосрочная | сводки тем за 24 часа и за неделю | локально |
| Кратковременная память | монолитный файл | локально |
| Компактная память (данные о владельце и т. п.) | монолитный файл | **не решено** (вопрос 1) |
| Notes: `Caroline:Vault`, `Profile`, `Memory`, `Topics` | как сейчас | SW, через адаптеры |

Серверная память хранится **файлами** в отдельном хранилище памяти Камерленго, в `/mnt/remote/ImmersiveLionSchool/Contents/Memory` — уже смонтированном и используемом **SSHFS** (путь — параметр конфигурации). Оно вне раздаваемого корня сайта и вне основного диска сервера. **Журнал операций** — отдельный, там же (формат — вопрос 9).

SQLite для памяти не используется: на SSHFS не работает WAL, блокировки не передаются на удалённую сторону, обрыв SSH посреди транзакции может испортить базу. Файловая схема для SSHFS:

- **Атомарная запись файла:** запись во временный файл рядом → переименование поверх старого. Требует атомарного переименования на sshfs (`posix-rename@openssh.com`) и fsync (`fsync@openssh.com`) — проверяется на этапе 2.
- **Журналируемая запись с восстановлением.** Любая операция, которая меняет больше одного файла (запись факта в несколько листьев, разбиение, слияние, обновление индексов), идёт через журнал намерений пользователя (write-ahead), отдельный от журнала операций и стоимости:
  1. все новые версии файлов пишутся во временные файлы, fsync;
  2. в журнал намерений дописывается запись `prepared`: id операции, список «временный файл → целевой файл», порядок переименований (потомки раньше родителя);
  3. дописывается `committed` (fsync) — **точка фиксации**: с этого момента операция считается выполненной;
  4. переименования по списку; обновление индексов;
  5. дописывается `done`.
  
  **Восстановление** при старте Камерленго и периодически: операция без `committed` откатывается (её временные файлы удаляются); операция с `committed`, но без `done`, доводится до конца (переименования идемпотентны, индексы пересобираются по затронутым листьям). После восстановления журнал намерений усекается.
- **Один писатель:** в хранилище пишет только один процесс Камерленго; нитки внутри него синхронизируются блокировками в памяти процесса. Второй писатель с другой машины недопустим.
- **Индексы производные:** всегда пересобираются из узлов; расхождение лечится пересборкой, а не теряет данные.
- **Кэш узлов в памяти процесса** с записью насквозь — безопасен при одном писателе и снимает большую часть сетевых чтений при спуске.
- **Чистка потеряшек** — после каждого восстановления и периодически (служебная операция): удаляет файлы узлов, на которые не ссылается ни один родитель, и временные файлы, не принадлежащие ни одной незавершённой операции журнала намерений, старше параметра-задержки; удаляет записи индексов, ведущие в никуда; факты, которые не лежат ни в одном листе (потерянные), **заново раскладывает по дереву** обычной журналируемой записью, с сохранением их постоянного id. Что сделано, пишется в журнал операций.

### 2.4. Долговременная память: дерево

- Дерево с параметризуемым ветвлением, по умолчанию 8–12 потомков на узел. Узел — файл; его размер ограничен так, чтобы узел свободно помещался в контекст малой модели. Ветвление задаётся на дерево; его изменение у заполненного дерева — отдельная операция перестройки.
- Внутренний узел — таблица маршрутизации: потомки с короткими описаниями. Лист — факты.
- **Чтение.** Микроагент узла получает всех n потомков под однобуквенными метками, которые выдаёт код на один вызов (A, B, C…; настоящие имена файлов модель не видит), и возвращает **ранжированный список всех n**. Спуск идёт в первые `m = min(n, max(2, ⌈0.25n⌉))`. Ранней остановки нет: обходятся все выбранные ветки на всех уровнях, находки из всех листьев объединяются. Ветки независимы и идут параллельно.
- **Санитайзер чтения.** Отбор в листе видит факты одного листа и берёт с запасом. Поэтому после слияния находок со всех веток и из индекса ключей отдельный микроагент смотрит на весь набор сразу и оставляет только факты, нужные для ответа на запрос (по одному или в сочетании). Если факты дают разные ответы на запрос, остаются все: спор должен быть виден. Сбой санитайзера не теряет найденное: набор отдаётся как есть с пометкой о неполноте.
- **Запись.** В одном запросе может быть несколько фактов, адресованных в разные узлы. Узел раскладывает список фактов по потомкам; один факт **может** попасть в несколько листьев.
- **Идентификатор факта.** Каждый факт при первой записи получает постоянный id. Индексы ведут от id и от ключей (имя, email, телефон, сервис, дата…) ко **всем** листьям с копиями. Обновление и удаление идут по индексу во все копии, а не спуском. При чтении копии схлопываются по id в коде.
- **Запись факта хранится отдельно** от листьев, листья держат ссылки на неё. Поэтому счётчик и история ниже одни на все копии.

### 2.4.1. Подтверждения и опровержения

У каждого факта есть:

- **счётчик** — целое число;
- **история событий** — все занесения и опровержения, каждое с меткой времени: `+1` (факт внесён), `−1` (внесён факт, который ему противоречит, с id этого факта). Счётчик всегда равен сумме истории и может быть из неё пересчитан.

Правила записи:

1. Факт, внесённый впервые, сохраняется со счётчиком 1.
2. **Повторное внесение** того же факта не перезаписывает его: в историю добавляется `+1`, счётчик растёт.
3. **Опровержение** — внесение факта, который противоречит уже известному (пример: «Руаль Амундсен — англичанин» против «Руаль Амундсен — норвежец»). Опровержение сохраняется как обычный факт со своим счётчиком (по правилам 1–2), а каждому факту, которому оно противоречит, в историю добавляется `−1`.
4. **Симметрично:** любое внесение факта уменьшает счётчики всех фактов, которые ему противоречат. Повторное «норвежец» после «англичанин» увеличит «норвежец» и уменьшит «англичанин».

При чтении факт отдаётся с отметкой по счётчику:

| Счётчик | Отметка |
|---|---|
| > 0 | обычный |
| = 0 | сомнительный |
| < 0 | отрицаемый |

Сомнительные и отрицаемые факты из ответа не убираются, а отдаются с отметкой: главная модель должна видеть, что версия оспорена.

**Порядок сохранения факта:**

1. **Сверка на входе, до любого занесения.** По индексу ключей по **всей памяти этого класса** находятся связанные факты — с теми же ключами, где бы в дереве они ни лежали.
2. Если связанные факты есть, микроагент сверки решает для каждого: новый факт его **подтверждает** (тот же факт), **опровергает** или с ним **не связан**.
3. **Только после этого — занесение:** подтверждение даёт `+1` существующему факту и новой записи не создаёт; иначе факт сохраняется и раскладывается по дереву; каждому опровергнутому — `−1`.

Сверка опирается на ключи, поэтому микроагент извлечения обязан давать **канонические ключи**: полное имя, а не фамилию или описание («Руаль Амундсен», а не «Амундсен» и не «первооткрыватель Южного полюса»). Это проверяется на золотом наборе.
- **Разбиение и слияние** выполняет LLM: разбиение при переполнении, слияние при заполнении меньше половины. Применение результата — журналируемая операция (раздел 2.3): новые узлы и родитель пишутся во временные файлы, фиксируются записью `committed` в журнале намерений, затем переименовываются (родитель последним); после сбоя операция откатывается или доводится восстановлением.
- **Описания** узлов обновляет тот микроагент, который меняет содержимое узла; при разбиении и слиянии — обязательно.

### 2.5. Извлечение фактов

**Память фактов внутри работает на английском** (решение 2026-10-09): текст на сохранение и запрос переводятся на английский на входе, найденные факты переводятся на язык разговора на выходе; язык называет Caroline. Переводят микроагенты на общей лестнице. **Пол людей.** Английский теряет род, поэтому переводчик на входе записывает пол каждого названного человека, если текст его показывает (не угадывая). Пол — свойство человека: хранится в реестре людей пользователя (имя → пол, побеждает более поздний текст) и прикладывается к каждому найденному факту — для переводчика на выходе (окончания, склонение имени) и для главной модели, отвечающей пользователю. Сохранение всегда проходит через входной проход, в том числе английское. **Имена собственные не переводятся и не транслитерируются**: остаются в исходном написании внутри английского предложения и в ключах («Руаль Амундсен was born in Борге»). Исходная формулировка каждой сохранённой части хранится рядом с переводом как источник, факт помнит свои источники. Темы, материалы трека и записи в Notes не переводятся.

**Единица факта** — полное предложение: о ком или о чём, что сказано, и не больше одной детали («Руаль Амундсен родился в 1872 году» и «Руаль Амундсен родился в Борге» — два факта). Обрывки запрещены; условие остаётся при том, что оно обусловливает.

Микроагент извлечения только раскладывает сказанное на атомарные факты. **Производных фактов нет**: ничего не выводится, факты не связываются в цепочки. Один и тот же смысл может быть сохранён с разных сторон (адресация и к субъекту, и к объекту).

Ключи факта — канонические: полное имя или название, а не сокращение или описание.

Длинный текст режется на части по самой широкой подходящей границе (абзацы, строки, предложения; размер части — параметр) и извлекается параллельно. Каждой части для справки показывается конец предыдущей, чтобы местоимения раскрывались в имена; факты из него не извлекаются. Одинаково сформулированный факт из нескольких частей берётся один раз. Существующий `ai:factExtract` для этого не используется (раздел 6).

Каждый извлечённый факт до занесения проходит сверку по всей памяти своего класса (раздел 2.4.1): подтверждение — `+1` к существующему, новых записей нет; опровержение — новый факт плюс `−1` опровергнутым.

### 2.6. Тематическая память

- Трек темы: сводка + журнал эпизодов. Темы иерархичны (подтемы).
- Отдельный контролёр со своим индексом и хранилищем, отдельно от дерева фактов.
- **Сумматор** — микроагент, срабатывает при каждом обновлении трека: пересобирает сводку и короткое описание темы.
- Три уровня по времени последнего эпизода: **последние 24 часа**, **последняя неделя**, всё остальное.
- В промпте Caroline — короткие описания тем за 24 часа и за неделю двумя группами. Сводки, результаты и история — только по `request_info`. Темы старше недели в промпт не попадают вообще.
- Старые заметки `Caroline:Topics` остаются в Notes и доступны через адаптер; новые темы пишутся только в новое хранилище.
- **Трек хранится целиком**, а не только как выжимка: вместе с эпизодом сохраняются его материалы — письма и сообщения полностью (отправитель, получатели, время, тема, текст) и документы (сам файл + извлечённый текст). **Что подавать в память, решает главная модель и передаёт это сама** в вызове инструмента; ни микроагенты, ни код вокруг них сами ничего не забирают (письмо по id, переписку, папку). Единственное, что добавляет код клиента, — байты документа, путь к которому модель назвала явно. Код хранит материалы ровно как прислано; модели (сопоставление, сумматор) видят только ограниченные параметрами выдержки. Материал с тем же источником и ссылкой в теме хранится один раз.
- Чтение по умолчанию: сводка, результаты, открытые вопросы и список последних материалов (кто, когда, тема — без текста). Полный текст материала — отдельным запросом, постранично; файл — по явному запросу.

### 2.6.1. UID и атрибуты

- У каждого элемента памяти свой **UID**: факт, тема, эпизод, материал трека; у заметки Notes — её id.
- **Атрибуты** (метаданные) — отдельная сущность со своим API: словарь ключ → значение на UID, хранится отдельно от элемента (`attributes/<xx>/<uid>.json`). Команды: установить (слияние, null удаляет ключ), получить по списку UID, очистить. Остальные виды памяти атрибуты пока не читают и не меняют — это задел на будущее.

### 2.7. Общее правило представления

Везде, где модель видит список тем, узлов или элементов, это **короткое описание**, а не голый заголовок.

### 2.8. Параметры вместо жёстко зашитых значений

Всё, что может быть параметром или именованной константой, делается параметром или константой; в коде логики числа и имена моделей не пишутся. Как минимум параметризуются:

| Параметр | Значение по умолчанию |
|---|---|
| Ветвление внутреннего узла | 8–12, задаётся на дерево |
| Ёмкость листа и предельный размер узла | под контекст малой модели |
| Ширина спуска: коэффициент и минимум в `m = min(n, max(MIN, ⌈K·n⌉))` | K = 0.25, MIN = 2 |
| Порог разбиения / слияния узла | переполнение / заполнение меньше половины |
| Окна тематической памяти | 24 часа и 7 дней |
| Состав лестницы: модели и порядок ступеней | нано, нано с причиной отказа, мини |

### 2.9. Память документов (решения 2026-10-10)

Помимо памяти фактов нужна память документов: документ хранится целиком, его содержимое проиндексировано, а факты из него лежат в памяти фактов со ссылкой на место в документе.

**Что уже есть в Камерленго и что берём:**
- **Извлечение текста:** берём `SHRDialogEngine/Adapters/AgenticDocuments.py` (PyMuPDF для PDF, python-docx, BeautifulSoup для HTML, FB2, TXT, исходники; нарезка по границам абзацев до заданного размера). Иерархию `Adapters/Documents/*` не берём: её определение заголовков ошибается, а модель данных рассчитана на ботов. Сканы и картинки — распознавание текста, как в `ai:textFromImages`.
- **Анализ куска:** идея промпта `Document._analyzeParagraph` (ключевые слова и пересказ на английском), но как микроагент рантайма — с лестницей, бюджетом, учётом стоимости и списанием. Попарную починку абзацев (`analyze`, шаг 1) не переносим: она удваивает число вызовов.
- **Не берём:** `SourceController` (общая папка `STORAGE/loaded_sources` на диске сервера, без пользователей), TF-IDF-поиск `Document.search` (только внутри одного документа), `VectorCache` (решено искать деревом, не векторами), `fsindex` (индексирует дерево файлов, не содержимое).

**Устройство:**
- **Попадание:** отдельный инструмент Caroline `save_document(path, note?)`: модель сознательно решает запомнить документ, не через `save_info`. Команда `memory:saveDocument`, файл передаётся целиком.
- **Текст извлекает сервер**, не модель.
- **Хранение:** в хранилище памяти пользователя (SSHFS), каждый документ один раз — повтор определяется по хэшу содержимого. У документа UID; внутри — исходный файл, извлечённый текст, куски со своими UID и карточка: название, язык, пересказ, источник, даты, заметка модели.
- **Индексация:** на каждый кусок микроагент даёт пересказ и ключевые слова на английском; из них — пересказ документа в карточке. Карточки документов раскладываются в **дерево**, устроенное как дерево фактов (раздел 2.4, `MemoryStore.TreeFiles`): ветки с описаниями, разбиение при переполнении, спуск при поиске.
- **Факты:** весь документ проходит через извлечение фактов памяти фактов (кусками, как длинный текст в `memory.facts.save`). Источник каждого факта — документ и кусок, так что от факта можно перейти к месту в документе. Главная статья расходов: растёт с размером документа.
- **Чтение:** диспетчер получает контроллер `documents`. Он спускается по дереву к документам, внутри найденных отбирает куски (по пересказам) и отдаёт карточку и выдержки с UID — порциями, как память фактов (`memory:requestStart` / `memory:requestPoll`). Раздел целиком — `request_info(document=…, section=…)`, как материалы тем.
- **Открыто:** что делать с документами, которые уже лежат материалами в темах (переносить в память документов и ссылаться на них, или оставить как есть) — решить на этапе 12.

## 3. Фреймворк микроагентов

Один модуль на обе стороны (сервер и клиент), без серверных зависимостей. Функция вызова модели передаётся снаружи: на сервере `AI().resolve`, на клиенте — команда API.

Файл модуля лежит **копией в обоих репозиториях** (reforce и Caroline), правки переносятся вручную. Чтобы копии не разошлись незаметно: в файле объявлена версия модуля, а тест в каждом репозитории сверяет свою копию с эталонной контрольной суммой для этой версии.

### 3.1. Объявление микроагента

Имя, версия, короткое описание (из описаний собирается промпт диспетчера), схема входа, схема выхода, построитель промпта, собственная проверка результата.

### 3.2. Конверт вызова

Вход:

```json
{
  "agent": "memory.dispatch",
  "input": {},
  "context": {
    "session": "...",
    "turn_id": "...",
    "trace_id": "...",
    "language": "Russian",
    "budget": {"calls": 0, "deadline_ms": 0}
  }
}
```

Выход:

```json
{
  "status": "ok | empty | error | no_funds_user | no_funds_upstream",
  "output": {},
  "usage": {"rung": 1, "calls": 0, "tokens": 0, "ms": 0},
  "trace": [],
  "error": {"code": "...", "message": "..."}
}
```

**Числовых оценок нет**: модели плохо отвечают числами. Результаты качественные, например ранжированный список.

### 3.3. Лестница запуска (общая для всех агентов)

1. нано-модель → санитайзинг;
2. нано-модель с усиленным промптом, в который включены прошлый ответ и **причина отказа** → санитайзинг;
3. мини-модель → санитайзинг;
4. сдача: `status: error`.

Выход по первому успеху. Санитайзинг: разбор JSON → проверка схемы → собственная проверка агента (для ранжирования: ровно предложенные метки, каждая один раз). Ступень, на которой агент прошёл, пишется в `usage.rung`.

Модели берутся из `Config.py`: нано — `AI_MODEL_SMALL` (сейчас `openai/gpt-5-nano`), мини — `AI_MODEL_MINI`.

**Глубина рассуждения — свойство ступени**, задаётся в `Config.py`: сейчас `low` / `low` / стандартная у провайдера. Замер 2026-10-08 на промпте извлечения для нано: стандартная — 33–83 с на вызов и иногда весь лимит токенов уходит на рассуждение без ответа; `low` — 12–16 с; `minimal` — 2–3 с.

Лестница поднимается только при ответе, не прошедшем санитайзинг. Неверный по смыслу ответ в правильной форме проходит на первой ступени, поэтому первая ступень не ставится на `minimal`: в замере она давала неверные сверки без единой эскалации.

Составной агент (тот, что только вызывает других) ограничен бюджетом запроса, а не сроком одиночного агента.

### 3.4. Нитки и обработка ошибок

Каждый микроагент работает в своей нитке (именно нитки, не процессы), не мешает другим, падение одного не влияет на остальных. Обязательные требования к реализации:

- Весь запуск агента обёрнут в границу исключений: любое исключение превращается в `status: error`, попадает в трассу и не выходит за пределы нитки.
- Жёсткий таймаут на каждый вызов модели и общий срок агента из бюджета. Зависшая нитка бросается и считается упавшей (в Python нитку нельзя убить).
- Нитки из пула ограниченного размера.
- Общего изменяемого состояния нет, кроме файлов хранилища и кэша узлов. Запись — под блокировками в памяти процесса с таймаутом, атомарной заменой файлов (раздел 2.3).
- Бюджет ведётся по всей цепочке: вложенный вызов получает остаток, а не новый лимит. Агент зовёт агента только через фреймворк.
- Учёт расходов в `AI.py` сейчас привязан к нитке (`threading.local`, `begin_usage_tracking`/`get_tracked_usage`). Фреймворк обязан собирать расходы из ниток агентов и отдавать их наверх, иначе часть вызовов не попадёт в биллинг.

Ограничение, принятое осознанно: нитки не защищают от падения всего процесса (нехватка памяти, крах нативной библиотеки).

| Ситуация | Поведение |
|---|---|

| Кончились деньги на OpenRouter (наша себестоимость) | Сброс к началу хода |

Что есть в reforce сейчас и что нужно сделать:

- Шлюз баланса `_check_balance_or_error` (порог `ANTHROPIC_PROXY_MIN_BALANCE_PIA`) отвечает 402 для кошелька пользователя. 402 от OpenRouter уже превращается в `InsufficientFundsError`, но наружу команды отдают его общей ошибкой. Нужны **разные коды** для кошелька и апстрима.
- **Минус до конца хода**: команды памяти несут `turn_id`; сервер помнит, что ход начался при положительном балансе, и пропускает его вызовы через шлюз. Различение делается на сервере, не на клиенте (код клиента открыт).
- **Потолок на ход** по числу вызовов, иначе бесконечный ход даёт бесконечный минус.
- **Цена для пользователя:** операция памяти списывает с SW-кошелька пользователя, в пиастрах (PIA), **двойную** реальную стоимость OpenRouter всех вызовов модели внутри операции. Реальная стоимость берётся из `usage.cost` ответа OpenRouter (`AI.py` уже фиксирует её в `_record_usage`, если запрос сделан с `usage: {include: true}`), суммируется по всем ниткам агентов, умножается на параметр-множитель (по умолчанию 2.0), переводится в PIA существующим конвертером и списывается тем же путём, что `_bill_usage` (`api_payment_controller.charge`). Сейчас остальные `ai:*` команды денег не списывают, только пишут запись с суммой TBD; для памяти это меняется.
- **Журнал операций и стоимости** — отдельный, в хранилище на SSHFS (раздел 2.3), не общий журнал `AI.py` на диске сервера. Формат: дописываемые построчные JSON-файлы с ротацией по дням в отдельном каталоге хранилища. Это не журнал намерений из раздела 2.3: тот служит восстановлению записи, этот — учёту. Каждая операция памяти пишется в журнал: пользователь, `turn_id`, `trace_id`, вид операции, какие агенты вызваны, на какой ступени лестницы каждый прошёл, модели, токены, стоимость OpenRouter в USD, списано с пользователя в PIA, статус. Журнал пишется и при отказе (без денег, ошибка), а не только при успехе.
- Сброс хода к началу при `no_funds_upstream` не откатывает побочные действия первой половины хода. Для SMS защита от дублей есть (`find_recent_duplicate_send`), для почты и остального её нет.

Каждая из трёх серверных правок (коды ошибок, минус до конца хода, потолок) согласуется отдельно перед изменением.

## 8. Тестирование

### 8.1. Модульные тесты фреймворка (подставная модель, без сети)
- Лестница: успех на 1-й ступени; отказ → 2-я ступень получает прошлый ответ и причину; отказ → мини; отказ → `error`. Проверяется `usage.rung`.
- Санитайзинг: невалидный JSON, несоответствие схеме, выдуманная/пропущенная/повторённая метка в ранжировании — каждый случай даёт отказ с понятной причиной.
- Граница исключений: исключение в агенте → `status: error`, соседние нитки завершаются нормально.
- Зависание: подставная модель не отвечает → агент считается упавшим по сроку, вызывающий не ждёт дольше бюджета.
- Пул: при широком спуске одновременно работает не больше заданного числа ниток.
- Бюджет: вложенный вызов получает остаток; исчерпание бюджета останавливает дальнейшие вызовы.
- Расходы: расходы из всех ниток агента попадают в итоговый `usage`.

### 8.2. Золотой набор на реальных моделях
Набор пополняется примерами, которые даёт пользователь. Для каждого фиксируется: прошёл ли, на какой ступени, сколько вызовов и времени. Запускается только по явному флагу (`MICROAGENT_LIVE=1`), потому что тратит деньги.

**Формат примера извлечения — без ожидаемого числа фактов.** Правильное количество зависит от текста, поэтому пример задаёт: обязательные факты (каждый должен найтись по смыслу), запрещённые факты (выведенные знания, тавтологии), канонические ключи и запросы с ожидаемым ответом. Прочие лишние факты тест не проваливают, а печатаются как замечания к дообучению.

Правила извлечения, уточнённые на примере 1: национальность и профессия — значимые признаки человека, каждый отдельным фактом; факты, близкие к тавтологии, не сохраняются («Южный полюс был открыт полярным исследователем» приемлем, но бесполезен). Факты одного сохранения между собой не сверяются: сверка идёт с тем, что было в памяти до него.

**Пример 1.** Вход: «Норвежский полярный исследователь Руаль Амундсен открыл Южный Полюс».
Должны сохраниться ровно эти факты (без производных):
- Руаль Амундсен — полярный исследователь
- Руаль Амундсен — норвежец
- Южный полюс был открыт Руалем Амундсеном
- Южный полюс был открыт норвежцем

Запросы:
- «Кем был открыт Южный Полюс?» → «Руалем Амундсеном»
- «Представители какой нации открыли Южный Полюс?» → «Норвежцы»

**Пример 2. Подтверждения и опровержения.** После примера 1 последовательно вносится:

| Вносится | «Амундсен — норвежец» | «Амундсен — англичанин» |
|---|---|---|
| (после примера 1) | 1, обычный | — |
| «Руаль Амундсен — англичанин» | 0, сомнительный | 1, обычный |
| «Руаль Амундсен — англичанин» | −1, отрицаемый | 2, обычный |
| «Руаль Амундсен — норвежец» | 0, сомнительный | 1, обычный |

После каждого шага история событий каждого факта содержит все `+1` и `−1` с метками времени, а сумма истории равна счётчику. Повторное внесение не создаёт второго факта.

Для тематической памяти — сценарии вида «обсуждали тему, пришли к результату, через сутки и через неделю спросили, что решили».

### 8.3. Целостность хранилища
- Свойства дерева после случайных последовательностей записей и удалений: каждый факт достижим по индексу; индекс не ссылается на несуществующие листья; размеры узлов в пределах; нет потерянных веток.
- Восстановление: сбой, внедрённый **на каждом шаге** журналируемой операции (до `prepared`, между `prepared` и `committed`, посреди переименований, до `done`), после восстановления даёт целостное состояние: операция без `committed` полностью отсутствует, операция с `committed` выполнена целиком. Повторный запуск восстановления ничего не меняет.
- Чистка потеряшек: удаляет непривязанные узлы и временные файлы старше задержки; не трогает файлы незавершённой операции из журнала намерений; удаляет висячие записи индексов; потерянный факт после чистки снова лежит в дереве под прежним id и находится запросом; всё сделанное попадает в журнал операций.
- Конкурентная запись из нескольких ниток не теряет фактов и не портит индексы.
- Факт в нескольких листьях: обновление и удаление доходят до всех копий; чтение отдаёт его один раз.
